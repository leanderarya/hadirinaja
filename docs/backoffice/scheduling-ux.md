# Schedule UX and technical contract

[Back to blueprint](README.md) · [Cepat Kopi rules](cepat-kopi-reference.md)

## Week selection and editing

1. Choose an authorized **outlet** and **week**. The identity of a week is `(active tenant, outlet, local Monday)`. Show the outlet timezone and local date range. Keep **No schedule**, **Draft**, and **Published** distinct.
2. For a genuinely new week, offer **Start Empty** or **Copy Previous Week**. Start Empty opens an unsaved week with unfilled slots; it does not create rest days or a server draft. Copy uses the immediately preceding local Monday for the same outlet, and only a published source revision. If unavailable, explain why and keep Start Empty available. Preview copied assignments and any conflicts before confirming; don't silently drop, substitute or duplicate employees. Copy never publishes or changes its source. Do not replace a saved draft silently.
3. The **daily list** edits assignments by date and shift, using only employees eligible at that outlet and date. Show staffing targets and empty slots. The **weekly calendar overview** reflects the same edits immediately and takes the Owner to the selected day. Use one edit buffer with stable entry IDs/keys and its base version; changing views must not submit or discard it. Display assignment-level errors in both views.
4. **Save Draft** persists an unpublished candidate only. **Publish** validates the saved candidate before it can become effective. If there are local unsaved edits, require Save Draft before Publish; do not validate one version and publish another. A publish request acts only on the reviewed `expected_version` and published base.
5. On an already published week, edit the published assignments directly in the same editor. **Save Changes** is the only action that advances the effective revision. Until it succeeds, Employee reads and attendance keep seeing the old published schedule. No user-visible second Publish action and no background writes to the effective roster.

## Warnings, blocks and recovery

| Case | Required behavior |
|---|---|
| Empty staffing slots | Show the exact day, shift and number short. Permit Publish, or Save Changes that immediately publishes a replacement, only after explicit confirmation bound to the latest candidate. Any candidate, staffing-policy or base-version change invalidates acknowledgement. |
| Invalid data or conflicts | Block publication/effective save on invalid dates, inactive or out-of-scope assignments, overlapping shifts (including other outlets and overnight/adjacent dates), forbidden tenant/outlet references, disallowed shift/day combinations or protected started/historical rows. Show actionable errors; no override on these failures. |
| Concurrent change | On stale `409`, keep unsaved data in memory, fetch the latest server state, and let the Owner compare and explicitly reapply. Do not silently merge or overwrite. |
| Validation or permissions | On `422`, surface field or row errors without discarding input. On `403` or `404`, stop writes for that scope. On session/CSRF expiry, recover through normal authentication, then revalidate draft and identity before allowing a retry. |
| Timeout or disconnect | Keep the exact payload and idempotency key. Reconcile by replaying that same request and re-reading state. Do not issue a different publish attempt, reuse a key with changed inputs, or claim success from a click or pending response. |
| Persistence failure | No partial effective schedule, lost prior publication, or orphan acknowledgement. Keep the prior effective view until a fresh read confirms the committed replacement. |

### Direct-save contract

Keep published revisions immutable. On explicit Save Changes, bind the request to tenant, outlet, week, expected lock version, expected published revision, candidate entries, reason and idempotency key. Review and acknowledge any deficit against a checksum that binds the candidate, staffing rules and base version. In one transaction, re-authorize, revalidate, create the replacement revision and snapshots, switch the effective pointer, record actor/reason/time/old and new revisions, and persist the idempotent result. Use the existing lock order. If an unconnected draft exists, return a conflict for the Owner to resolve; do not overwrite it as a side effect.

After commit, refresh Owner and Employee reads. The Employee must get the replacement on the next authorized read/reload, with any on-screen stale cache invalidated or refreshed; no push delivery requirement is inferred. Existing `weekly_planner_start_on` gates planner consumption. An outlet not yet cut over must not imply that a saved publication is already effective. First cutover is a separate explicit Owner decision using the existing future-Monday constraint, not a hidden side effect of routine Save Changes. Retain past attendance snapshots and started shifts.
