## Finding 8 root cause, established before implementation

Reproduced the documented Owner sequence on the prior production-built frontend and a disposable synthetic MySQL database: approve request 1, select it under approved status, and repeatedly toggle retention. DOM inspection counted seven evidence headings with distinct generated IDs. No source implementation had yet changed.

In `src/routes/approvals.tsx`, `CorrectionEvidencePanel` and `CorrectionReversalForm` are siblings inside one article. Their keys were respectively the bare request ID and bare decision ID. The independent ID sequences can overlap: request 1 / approval decision 1 produces two sibling keys `1`. This violates React's sibling identity contract and leads to unsupported reconciliation: fresh panel mounts accumulate while prior panel DOM is retained/omitted incorrectly during parent updates.

Two deterministic regressions render the real approval route and real evidence/reversal components with request/decision IDs 1 and 2, deferred evidence responses and Owner updates. Before the fix, both fail: expected one evidence panel, observed two and four. React emits duplicate-key diagnostics for keys 1 and 2. These are the reproduction failures, distinct from initial test-fixture setup errors corrected while constructing the harness.

The selected request is derived from queue state; refresh replaces its object and reruns the selected projection effect. Finalization refreshes queue and projection, producing legitimate parent rerenders that expose the collision. The evidence effect already has an AbortController, cancellation checks and dependency cleanup; its callback is memoized by selected ID. There is no external evidence subscription or query-cache invalidation layer here: local state and API effects drive refresh. No extra subscription, effect retry or stale-response workaround is needed. The same-key collision, not the presence of loading states, is the demonstrated root cause.

The fix namespaces the evidence and reversal keys independently, keeping each tied to its binding ID. The existing API, effect cleanup, and authorization continue to govern the panel.
